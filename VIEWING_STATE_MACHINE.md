# Просмотр VR: блокеры, старт и окончание

Актуальность: 28 августа 2026. Это разбор фактической логики `control_server`, Django-токенов и сообщений гарнитуры. «Просмотр» в этом документе — один фильм на одной гарнитуре (`location:id`).

## Термины и источники состояния

| Состояние | Где хранится | Значение |
|---|---|---|
| `activity` | сообщение `updateState` гарнитуры | `0` — экран готовности/нет фильма; `1` — гарнитура сообщает состояние фильма; `2` — экран блокировки/сброса. |
| `userPresent` | гарнитура | датчик присутствия зрителя. Именно он запускает отсчёт окончания платного сеанса. |
| `pendingQueue` | control_server | выбранные фильмы, ещё не отправленные гарнитуре. |
| `queue` | control_server | фильмы, уже отправленные гарнитуре/ожидающие её подтверждения. |
| `currentVideoId`, `isPlaying` | control_server | фильм, который гарнитура сообщает как текущий, и его фактическое состояние. |
| `PaymentToken` / `PaidFilm` | `srv` | право на фильм. Платный токен действует до срока; отдельно существует флаг активного headset lease. |
| `viewer_session_id` | заказ + localStorage браузера | случайный UUID посетителя. Он объединяет только его последовательные покупки и не позволяет второму телефону захватить гарнитуру. |
| `paidAuthorizations` | control_server | краткая авторизация конкретного фильма для создания статистического сеанса. |
| `paymentSessionResetPending` | control_server | сервер уже начал закрывать платёжную сессию; до успешного окончания новый платный старт запрещён. |
| `activePlaybackSession` | control_server + statisticsDataServer | статистический сеанс оплаченного воспроизведения. |

Нужно не смешивать три разных понятия: **право оплаты**, **команда запуска** и **фактическое воспроизведение**. Они приходят из разных процессов и могут временно расходиться.

## Условия старта

### 1. Старт по кнопке «Смотреть» в мобильном браузере

Последовательность успешного старта:

1. Мобильная страница знает контекст `location:id` гарнитуры.
2. В браузере токен существует, не истёк и содержит выбранный фильм.
3. В WebSocket-запросе `videoForClient` найдена подключённая гарнитура с той же парой `location:id`.
4. `control_server` вызывает Django `tokens/resume_viewer_session` с токеном и фильмом.
5. Django требует одновременно: токен активен и не истёк; фильм есть в `PaidFilm`; заказ имеет статус `paid` или `checked`; `viewer_id` совпадает с `location/id` после нормализации числового номера (`02` = `2`).
6. Если lease свободен, токен этой покупки его получает. Если lease уже принадлежит другой browser-session, запуск отклоняется как «Очки сейчас используются другим зрителем». Следующие фильмы той же browser-session разрешены даже если их собственный token не несёт флаг lease.
7. `paymentSessionResetPending` равен `false`.
8. Этот фильм ещё не является `currentVideoId` и отсутствует в `queue` и `pendingQueue`.
9. Если зритель присутствует и гарнитура не на экране блокировки — фильм попадает в `queue`, гарнитуре посылается `videoChangeRequested`.
10. Если `userPresent === false` либо `activity === 2` — фильм попадает только в `pendingQueue`; отправка произойдёт, когда гарнитура сообщит `activity === 0`, `userPresent === true`.
11. Гарнитура должна прислать `activity === 1`, `details.videoId` и `isPlaying === true`. Только тогда создаётся `activePlaybackSession` и отправляется статистическое событие `start`.

### 2. Старт, выбранный непосредственно в гарнитуре

Если гарнитура сообщает `activity === 1` с новым `videoId`, которого нет в `queue`, сервер сам вызывает защищённый Django endpoint `viewer_film_access`.

Старт разрешён, только если для этой гарнитуры существует активный, неистёкший, оплаченный токен на этот фильм с действующим headset lease и нет `paymentSessionResetPending`. При успехе сервер добавляет фильм в `queue`, создаёт одноразовую `paidAuthorizations` и ждёт фактического `isPlaying` для статистики. После приостановки lease прямой старт в гарнитуре сам его не возобновляет: зритель должен один раз нажать «Смотреть» в сохранённой мобильной сессии.

Если проверка недоступна — запуск блокируется с сообщением о невозможности проверить оплату. Если оплата отсутствует — сервер отправляет `videoStopRequested`, ждёт выхода гарнитуры из фильма и показывает экран с инструкцией оплаты по QR.

## Полный список блокеров старта

| Блокер | Где срабатывает | Результат |
|---|---|---|
| Нет контекста или нужной гарнитуры нет в списке WebSocket | браузер / `videoForClient` | «Клиент не найден»; команда не отправляется. |
| Не указан `videoId` | control_server | запрос отклоняется. |
| Нет токена в браузере | браузер | кнопка не запускает запрос. |
| Токен неактивен или истёк | браузер и Django | «Нет доступа» / «Время доступа истекло». |
| Фильм не входит в оплаченный токен | браузер и Django | просмотр запрещён. |
| Заказ токена не `paid` и не `checked` | Django | оплата считается неподтверждённой. |
| Токен куплен для другой гарнитуры | control_server | `viewer_id` не совпадает с нормализованным `location/id`; старт запрещён. |
| Гарнитура занята другой browser-session | Django `resume_viewer_session` | токен действителен, но lease не передаётся; показывается «Очки сейчас используются другим зрителем». |
| Ошибка/недоступность API проверки оплаты | control_server | запуск из гарнитуры останавливается с отдельным сообщением; запрос кнопки также не получает авторизации. |
| Закрытие прошлого сеанса уже началось | control_server | `paymentSessionResetPending === true`; новый платный старт отклонён до успешного reset. |
| Тот же фильм уже текущий, в отправленной или отложенной очереди | control_server | не ошибка: ответ `duplicate: true`, повторный запуск не посылается. |
| Гарнитура не готова (`userPresent === false` или `activity === 2`) | control_server | не отказ: фильм откладывается в `pendingQueue`. |
| Гарнитура не прислала `isPlaying === true` | протокол гарнитуры | команда считается отправленной, но статистический просмотр не начался. |
| Запоздалое состояние после stop | control_server | игнорируется по `stopRequestedVideoId`, не авторизуется и не блокируется повторно. |
| Запоздалый autostart из уже истёкшей сессии | control_server | отправляется stop без нового блока оплаты. |
| Неактивный «хвост» старого видео (`isPlaying === false`) | control_server | игнорируется до реального старта, чтобы не заблокировать экран после разблокировки. |

## Условия окончания просмотра

| Причина | Триггер | Что происходит |
|---|---|---|
| Нормальный конец фильма | гарнитура выходит из `activity === 1` | фильм удаляется из `queue`; статистика закрывается как `playback_ended`. |
| Пользователь нажал «Остановить» | команда `stop` + следующий state не `1` | фильм удаляется из обеих очередей; в статистике причина `stopped`. |
| Выбран/стартовал другой фильм | новый `videoId` при имеющемся `currentVideoId` | предыдущая статистика завершается как `video_changed`; старый фильм удаляется из `queue`. |
| Сняли гарнитуру после того, как присутствие уже было | `userPresent=false` непрерывно 10 минут по умолчанию | сервер отправляет stop, завершает статистику как `viewer_presence_timeout`, чистит очереди и **приостанавливает lease**, но не деактивирует оплаченный токен. |
| Гарнитуру надели снова до истечения 10 минут | `userPresent=true` | ожидающий таймер отменяется; просмотр/право не закрываются. |
| Соединение гарнитуры оборвалось | WebSocket close | состояние сохраняется на 30 секунд. Если reconnect не произошёл — статистика завершается как `disconnect_timeout`; токен при этом не деактивируется. |
| Попытка запустить неоплаченный фильм | прямой выбор в гарнитуре | сервер останавливает фильм и вместо нормального просмотра показывает блок оплаты. |
| Сервер уже закрывает сессию, но reset API временно падает | ошибка `end_viewer_session` | очереди уже очищены и воспроизведение остановлено; новый старт остаётся заблокированным, reset повторяется через 10 секунд по умолчанию. |

### Классификация завершённого оплаченного просмотра

Это не блокировка, а результат для статистики:

- `viewed`: максимальная позиция ≥ 50% длительности;
- `abandoned`: проиграно более 20 секунд, но не достигнут порог 50%;
- `short`: 20 секунд или меньше;
- `unclassified`: недостаточно данных о длительности/воспроизведении.

## Перекрёстные влияния и уязвимые места

### P0 — `addToQueue` обходит проверку оплаты

`videoForClient` проверяет токен и записывает `paidAuthorizations`. Однако отдельная WebSocket-команда `addToQueue` только кладёт `videoId` в `pendingQueue`: она не проверяет токен, фильм и принадлежность гарнитуре. Когда `pendingQueue` продвигается в `queue`, `handleStartVideo` видит, что фильм **уже в `queue`**, и поэтому не выполняет `viewer_film_access` повторно.

Следствие: любой вызывающий, имеющий доступ к WebSocket API, может сформировать запуск неоплаченного фильма через `addToQueue`; статистический сеанс не создастся (нет `paidAuthorizations`), но воспроизведение может начаться. Сейчас пользовательская кнопка добавления в очередь закомментирована, поэтому путь не штатный, но серверный API остаётся небезопасным.

Нужно выбрать одно правило и обеспечить его во всех ветках: либо удалить/закрыть `addToQueue`, либо требовать там тот же токен и авторизацию, либо всегда проверять доступ при переводе из `pendingQueue` в `queue` и перед фактическим запуском.

### P0 — `fillQueue` позволяет подменить отправленную очередь

Вторая устаревшая WebSocket-команда `fillQueue` принимает массив `payload.queue` и напрямую заменяет серверный `queue`, без проверки токена, lease и состава фильмов. Далее `handleStartVideo` опять считает наличие фильма в `queue` причиной не выполнять `viewer_film_access`. Таким образом, это тот же обход оплаты, но с возможностью подставить сразу несколько ID.

До исправления обе команды должны быть недоступны извне или игнорироваться сервером. Правильнее удалить `fillQueue`, а `addToQueue` направить через единый авторизованный путь `videoForClient`.

### P1 — очередь является одновременно командой и признаком доступа

`queue` отвечает сразу на два вопроса: «команда уже была отправлена?» и «не надо ли проверять доступ?». Это разные сущности. Из-за такого совмещения старый/внешне добавленный элемент очереди меняет ветку проверки оплаты. Нужны раздельные поля, например `requestedVideoIds` и `authorizedVideoIds`, или объект очереди с `videoId`, `authorization`, `requestedAt`.

### P1 — получение токена по одному `order_id`

`get_token_by_order` доступен без пользовательской аутентификации и возвращает токен по одному `order_id`. Сейчас `order_id` — случайный UUID, поэтому это не прямой перебор, но он используется как capability: утечка URL, localStorage, реферера или лога даст другому человеку действующий токен и возможность войти в сессию. В новом `latest_for_user` уже требуется доказательство покупки (`known_token` или `order_id`), но сам `get_token_by_order` следует связать с одноразовым browser proof, подписанной cookie либо сделать его короткоживущим.

### P1 — критическое окно приостановки lease

Когда 10 минут уже истекли, `paymentSessionResetPending` включается до HTTP-вызова Django и отменить эту фазу повторным `userPresent=true` нельзя. Если зритель надел гарнитуру в этот момент, экран может быть уже очищен, а новый просмотр будет запрещён до успеха reset. Токен остаётся действительным, но для нового запуска нужно дождаться окончания reset и возобновить lease через мобильную сессию.

Нужно явно решить продуктово: «10 минут — безусловная пауза» либо «вернувшееся присутствие до успешной приостановки отменяет reset». Сейчас реализован первый вариант после начала HTTP-вызова и второй — до него.

### P1 — неполное подтверждение окончания после команды stop

`stop` лишь отправляет команду и ждёт следующий `updateState` с `activity != 1`. Если гарнитура не прислала это состояние, `activePlaybackSession` не закрывается немедленно. Далее он может завершиться по disconnect, смене фильма или тайм-ауту присутствия с другой причиной. Для корректной статистики полезен watchdog подтверждения остановки.

### P2 — `userPresent` управляет и запуском, и приостановкой lease

Для отложенной очереди требуется `activity=0` **и** `userPresent=true`. То же поле через 10 минут приостанавливает текущий lease. Ошибка/шум датчика одновременно удерживает старт в очереди и может потребовать последующего возобновления lease. Следует логировать переходы датчика и отделить «можно отправить команду» от «пора приостановить доступ» хотя бы разными debounce/таймерами.

### P2 — разные таймеры жизненного цикла

Имеются как минимум: reset гарнитуры из `application.json` (60 с), серверный presence timeout (10 минут по умолчанию + grace), повтор reset API (10 с), защита от повторной блокировки после unlock (30 с) и reconnect grace (30 с). Они не объединены в один автомат. При смене одного значения нужно согласованно менять остальные и прогонять переходы: снять/надеть, stop, disconnect/reconnect, unlock и выбор неоплаченного фильма.

### P2 — active lease приостанавливается пачкой

`end_viewer_session` снимает `headset_session_active` со всех обычных active lease этого `location/id`, созданных к моменту `ended_at`, а не с одного конкретного заказа/просмотра. Токены остаются действительными. Это исключает короткий timeout как безвозвратную потерю покупки, но требует явного возобновления lease и покрытия тестом нескольких одновременных покупок.

## Рекомендуемая целевая модель

Сделать явные независимые автоматы:

```text
Право:     absent → valid → leased → suspended → leased
Команда:   none → pending → sent → acknowledged → cleared
Плеер:     idle → starting → playing → stopping → idle
Статистика:none → opened → finalized
```

Переход `starting → playing` разрешён только при действующем праве для `videoId`; переход `pending → sent` повторяет эту проверку. Завершение права не должно зависеть от очереди, а `queue` не должна быть доказательством оплаты.

## Файлы-источники

- `control_server/handlers/index.js` — запуск, очередь, блокировка, обработка `updateState`.
- `control_server/services/paidPlayback.js` — авторизация, таймаут присутствия, статистика, reconnect grace.
- `srv/database/api.py` — validation токенов, доступ гарнитуры и деактивация сессии.
- `statisticsDataServer/statisticsDatabase/views.py` — итоговая классификация просмотра.
- `control_server/test/queue.test.js`, `control_server/test/paidPlayback.test.js` — уже зафиксированные переходы и регрессии.
