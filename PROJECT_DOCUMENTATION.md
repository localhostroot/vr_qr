# VR QR Cinema — техническая документация

Актуальность: 28 августа 2026 года. Документ описывает фактическое устройство репозитория `vr_qr` и production-контура, проверенного в рабочем чате «Правки на сервере». Значения паролей, токенов, ключей, IP-адрес управления и другие секреты сознательно не приводятся.

## 1. Назначение

Сервис управляет VR-кинотеатром: гарнитура показывает каталог и проигрывает ролики, посетитель открывает мобильную страницу по QR-коду гарнитуры, выбирает и оплачивает фильмы, а оператор следит за устройствами и может ими управлять. Система также ведёт статистику **оплаченных** просмотров.

Основной публичный домен production: `cinema.local.vr360.pro`. Статистика развёрнута отдельным Django-приложением на `stats.local.vr360.pro`.

```text
VR-гарнитура ─WebSocket─┐
                         │
Мобильный браузер ───────┼── Nginx ── SvelteKit (8004): витрина, QR, оплата, статистика
                         │       ├── Django srv (8000): каталог, заказы, токены, PayKeeper
Админ-интерфейс ─────────┤       ├── Node control_server (11000): WebSocket и состояние VR
                         │       └── Django statistics (8002): сеансы оплаченного воспроизведения
                         └──────── PayKeeper ── банк-эквайер
```

## 2. Технологии и состав репозитория

| Каталог | Назначение и технологии |
|---|---|
| `qr_svelte5/` | Основной пользовательский web-интерфейс: Svelte 5, SvelteKit 2, Vite, adapter-node. Также содержит интерфейс статистики и серверные route handlers для auth/payments/stats. |
| `control_server/` | Node.js ES modules, Express, `express-ws` и `ws`. В памяти держит подключённые гарнитуры и их очереди, передаёт команды по WebSocket. |
| `srv/` | Главный Django 5 + Django REST Framework. Каталог, медиа, заказ, PayKeeper, платёжный токен, lease браузерной сессии и доступ к фильмам. SQLite в production. |
| `statisticsDataServer/` | Отдельный Django/DRF-сервис SQLite для статистики: события запусков и завершений оплаченных сеансов. |
| `admin-interface/` | Предыдущая React-админка. В production больше не является основным публичным интерфейсом; исходники сохранены как исторический/вспомогательный компонент. |
| `_headset/` | Конфигурации приложения на гарнитурах: `application.json` и `gallery.json`, плюс варианты отдельных площадок. |
| `system_stuff/` | Production-конфигурация Nginx, unit systemd и безопасные скрипты размещения/отката. |

В корневом репозитории нет единого монолита: это согласованный набор четырёх процессов и конфигураций гарнитур. Python-зависимости закреплены в `srv/requirements.txt`, `statisticsDataServer/requirements.txt` и `adminDataServer/req.txt`; JS-зависимости — в соответствующих `package.json`.

## 3. Production: сервер, процессы и маршрутизация

### 3.1. Пути на сервере

Рабочий корень production — `/opt/qr_app`.

```text
/opt/qr_app/
├── srv/                    Django API и SQLite db.sqlite3
│   ├── venv/               Python-окружение
│   ├── media/              загруженные изображения/медиа
│   └── staticfiles/        собранная Django-статика
├── statisticsDataServer/   статистический Django-сервис и его db.sqlite3
│   └── venv/
├── control_server/         WebSocket-сервер Node.js
│   └── uptime.json         локальная история времени подключения гарнитур
├── qr2/                    SvelteKit runtime
│   └── build/              текущая production-сборка
├── backups/                резервные копии перед размещениями
└── quarantine/             прежние/неудачные сборки, не удаляются сразу
```

Сервисы systemd:

| Служба | Порт | Роль |
|---|---:|---|
| `srv.service` | 8000 | основной Django/Gunicorn API |
| `stats.service` | 8002 | Django/Gunicorn статистики |
| `control_server.service` | 11000 | Node WebSocket-контроллер |
| `qr2.service` | 8004 | SvelteKit Node production build |
| `nginx` | 80/443 | TLS и обратное проксирование |

`qr2.service` запускает `/opt/qr_app/qr2/start-server.js`; этот launcher задаёт `HOST=0.0.0.0` и `PORT=8004`. Его unit описан в `system_stuff/qr2.service`.

### 3.2. Nginx и внешний URL-пространство

Источник конфигурации — `system_stuff/cinema.local.vr360.pro.conf`. HTTP принудительно перенаправляется на HTTPS. В production у Nginx разделены маршруты:

| Внешний путь | Получатель | Смысл |
|---|---|---|
| `/` и страницы SvelteKit | `127.0.0.1:8004` | витрина, QR-навигация, оплата, статистика |
| `/control/…` | `127.0.0.1:11000` | WebSocket гарнитур и браузерных команд; Upgrade заголовки передаются |
| `/api/auth`, `/api/stats`, `/api/payments` | `127.0.0.1:8004` | server-side API SvelteKit |
| `/api/...` кроме трёх путей выше | `127.0.0.1:8000` | Django REST API |
| `/admin/...` | `127.0.0.1:8000` | Django admin |
| `/static/` | alias `srv/staticfiles/` | статика Django с cache 30 дней |
| `/media/` | alias `srv/media/` | загруженные медиа |

Актуальные пользовательские адреса больше не имеют префикса `/new` или `/vr`: например, страница зрителя — `/{location}/{id}`. Скрипт `deploy-root-urls.sh` специально проверяет, что старые `/vr/...` и `/new/vr/...` возвращают 404.

### 3.3. Безопасное размещение и откат

Скрипты из `system_stuff/` не являются обычным `git pull`: они принимают архивы с allow-list файлов, делают резервную копию, запускают тесты и health checks, а при ошибке восстанавливают сервисы и файлы.

- `deploy-root-urls.sh` — атомарно меняет SvelteKit build и Nginx; старый build помещает в `quarantine`, копию — в `backups`.
- `deploy-viewer-session.sh` — изменения логики сессии/очереди, Django API и frontend. Перед включением выполняет Django-тесты, `node --test`, затем проверяет сервисы и API.
- `deploy-paid-statistics.sh` — изменения платёжной статистики: сохраняет обе SQLite БД средствами `sqlite3 .backup`, применяет миграцию статистики, тестирует четыре процесса и запускает health checks.
- `deploy-follow-up-lease.sh` — узкое обновление Django-логики покупки/lease: принимает ровно три файла, делает SQLite backup, прогоняет тесты `database` и имеет rollback.
- `update_qr2.sh` — старый упрощённый сценарий замены `build`; для новых изменений предпочтительнее безопасные сценарии выше.

Важно: папки `backups` и `quarantine` — часть процедуры восстановления, не временный мусор. Перед ручной чисткой надо подтвердить, что нужные контрольные точки больше не требуются.

## 4. Браузерные маршруты и состояния

SvelteKit расположен в `qr_svelte5/src/routes/`.

| Путь | Назначение |
|---|---|
| `/` | главная витрина |
| `/{location}/{id}` | контекст конкретной гарнитуры, полученный по QR |
| `/{location}/{id}/films`, `/film/{filmId}`, `/content/{contentId}` | выбор и описание контента в контексте гарнитуры |
| `/{location}/{id}/queue` | очередь выбранной гарнитуры |
| `/films`, `/film/{id}`, `/content/{id}`, `/queue` | совместимые общие маршруты |
| `/enter-token` | ввод/восстановление платёжного токена |
| `/payment-result` | возврат с платёжной формы |
| `/stats` | статистика |
| `/site-admin` | браузерный мониторинг площадки |
| `/debug` | отладочная страница |

Контекст зрителя хранит пару `location` + `id`; `viewerRoutes.js` строит адреса от неё. Потеря этого контекста была отдельной причиной ошибок в старых маршрутах, поэтому текущие переходы должны использовать helpers, а не собирать URL вручную.

## 5. Работа гарнитуры и control_server

### 5.1. Настройка гарнитуры

`application.json` задаёт, в частности:

- `controlServer`: защищённый WebSocket `/control/`;
- `location`: идентификатор в виде `ПЛОЩАДКА:НОМЕР`;
- `preset.resetTimeout`: таймаут сброса сеанса (типично 60 секунд);
- параметры рендера, gaze-pointer, экран блокировки и UI плеера.

`gallery.json` описывает каталог: папки и ролики, их `id`, URL видео/превью, панораму (`p180`/`p360`), глубину (`2d`/`3dSBS`), длительность и `dbContentId`. Для оплаты, очереди и команд плееру ключевым является `video.id`; `dbContentId` — дополнительный ID учёта и поиска метаданных и не считается уникальным ключом каталога.

Утверждённый `gallery.json` является источником истины для состава контента. Его текущая структура:

| Уровень | ID |
|---|---|
| Корневые фильмы | `russia`, `volga` |
| Папка `geo_02` | `geo_02_01`…`geo_02_06` |
| Папка `kb_00` | `kb_01`, `kb_02` |
| Папка `tyva` | `tyva_01`…`tyva_04` |

В Django корневому ролику соответствует `Category(serial=False)` с одинаковыми `cat_id` и `film_id`, а также единственная проигрываемая запись `Movie` с тем же ID и ссылкой на эту категорию. Папке соответствует `Category(serial=True)`, также с одинаковыми `cat_id` и `film_id`; её серии хранятся в `Movie.film_id`. ID уникальны внутри каждой таблицы. Команда `python manage.py audit_gallery_catalog` сверяет обе стороны целиком и должна выполняться после миграций и перед запуском сервиса.

Файлы в `_headset/` — шаблоны и варианты площадок; в `control_server/configs/` лежит используемая сервером конфигурация. Базовый `_headset/gallery.json` и общие площадочные варианты синхронизированы с утверждённым файлом; специальные урезанные варианты, например `tyva_only`, проверяются отдельно и не заменяют полный боевой каталог.

### 5.2. Протокол WebSocket

Один Node-процесс слушает 11000. Маршрутизатор различает:

- `/.websocket` — протокол гарнитуры;
- `/api/.websocket` — команды браузера/администратора.

При `login` гарнитура сообщает `location:id`. В памяти создаётся состояние клиента: соединение, очередь, отложенная очередь, текущий фильм и позиция, активность, присутствие зрителя, данные платёжной сессии и метки времени. При disconnect клиент убирается из активного списка, статус сохраняется в `presenceHistory`, а время подключения дописывается в `uptime.json`.

Браузерный мониторинг раз в 5 секунд запрашивает `getVrOverview`; при потере ответа за 15 секунд закрывает зависший сокет и переподключается с экспоненциальной паузой до 30 секунд. Также он восстанавливает соединение при `online`, focus и возврате вкладки.

Основные команды API: `getVr`, `getVrList`, `getVrOverview`, `getClient`, `videoForClient`, `addToQueue`, `removeFromQueue`, `clean`, `stop`, `mainMenu`, `reset`, `notification`. Гарнитура отправляет `login` и `updateState`.

### 5.3. Очередь и защита от повторного запуска

Очередь существует отдельно для каждой пары `location:id`.

1. Браузер проверяет токен и право на конкретный фильм, затем шлёт `addToQueue` либо `videoForClient`.
2. Сервер нормализует `queue` и `pendingQueue`: удаляет пустые элементы и дубликаты.
3. Повторная заявка не запускает фильм заново, если этот фильм уже текущий, находится в `queue` или в `pendingQueue`.
4. При готовности гарнитуры следующий `pendingQueue` переводится в команду `videoChangeRequested`.
5. События `updateState` подтверждают реальное воспроизведение, обновляют позицию и завершают фильм.

После последних правок сервер также игнорирует запоздалое inactive-состояние гарнитуры и защищает короткий переход разблокировки от ложной повторной блокировки. Это устраняет повторные старты и неверное завершение сессии после таймаута.

## 6. Каталог, заказ, оплата и доступ

### 6.1. Главный Django API (`srv`)

Роутер DRF публикует ресурсные группы:

`/api/category/`, `/api/movie/`, `/api/payments/`, `/api/status/`, `/api/tokens/`, `/api/admin/`, `/api/payments-test/`, `/api/payments-analytics/`.

Ключевые сущности в `srv/database/models.py`:

- `Category`, `Movie` — карточки фильмов/серий, цены, изображения и метаданные;
- `Order`, `OrderItem` — намерение оплаты и выбранные позиции;
- `PaymentToken` — выданный после успешной оплаты ограниченный по времени токен;
- `PaidFilm` — фильмы/серии, разрешённые конкретным токеном.

Алгоритм:

1. Зритель выбирает контент для конкретной гарнитуры.
2. Django формирует заказ и сервером создаёт инвойс в PayKeeper.
3. SvelteKit открывает полученную платёжную ссылку, а результат возвращается на `/payment-result`.
4. Django сверяет статус оплаты с провайдером, отмечает `Order`, создаёт `PaymentToken` и привязанные `PaidFilm`.
5. У заказа есть случайный `viewer_session_id`, сохраняемый в браузере. Он отличает последовательные покупки одного посетителя от другого посетителя у тех же очков.
6. При первом платном заказе на незанятой гарнитуре или при следующей покупке той же browser-session Django выдаёт ей один активный headset lease. Фильмы всех действительных токенов этой browser-session объединяются для доступа.
7. Перед командой `Смотреть` `control_server` через `resume_viewer_session` проверяет токен, фильм и владельца lease. Lease другого посетителя возвращает «Очки сейчас используются другим зрителем» и не заменяется.
8. Только после этой серверной проверки фильм помещается в штатную очередь и может быть запущен. Фактический старт подтверждает сама гарнитура (`isPlaying`).

Если заказ остаётся `pending`, код умеет найти и вернуть уже созданный инвойс вместо создания второго. Ошибочные попытки оплаты не выводятся как готовые к ручному подтверждению. Комплект сериалов поддерживает отдельные цены набора.

### 6.2. Бесплатный режим

Список разрешённых бесплатных гарнитур и длительность выдачи задаются на сервере. Для таких устройств `srv` выдаёт доступ без оплаты на установленный срок. Бесплатные токены не участвуют в обычной приостановке платного headset lease по отсутствию зрителя. Длительность бесплатного доступа не следует «зашивать» во frontend.

### 6.3. PayKeeper: граница ответственности

Приложение использует API PayKeeper для создания счёта и проверки статуса. Банковская связка PayKeeper → эквайер находится **не** на сервере cinema: банковские технические реквизиты хранятся у PayKeeper.

В ходе серверного чата установлено: ручной счёт в кабинете PayKeeper также не создавал СБП QR, тогда как прямое создание QR в кабинете банка работало. Следовательно, сбой был локализован между PayKeeper и банковским техническим API-пользователем, а не в коде витрины, callback или на сервере cinema. При смене банковского технического пароля его синхронизирует PayKeeper через защищённый канал; в этот репозиторий и в документацию он не записывается.

## 7. Статистика оплаченного воспроизведения

`statisticsDataServer` принимает `POST /api/update_statistics/` от control_server. Основная сущность — `PlaybackSession`, уникальная по `session_id`, с местом, устройством, видео, максимальной позицией, длительностью, активными секундами, причиной завершения и статусом.

Событие `start` создаёт сеанс и увеличивает `launches`. Финальное событие классифицирует его:

- `viewed` — просмотрено не менее 50% ролика;
- `abandoned` — больше 20 секунд, но меньше порога просмотра;
- `short` — 20 секунд или меньше;
- `unclassified` — данных недостаточно для иной классификации.

Счётчики есть на уровнях `Location`, `Device`, `Video`. Эндпоинты статистики: категории, видео, локации, устройства, login, total_stats и update_statistics. В production приём статистики должен быть защищён общим секретом control_server/statistics, хотя некоторые view сейчас помечены `AllowAny`; это требует отдельной технической проверки конфигурации и не должно заменяться публикацией секрета.

## 8. Переменные окружения и настройки

Значения не перечисляются. Production-хранилища окружения должны быть закрыты для чтения и не попадать в Git.

| Переменная | Используется в | Назначение |
|---|---|---|
| `DJANGO_SECRET_KEY` | `srv` | криптографический ключ Django |

На сервере главный Django unit использует отдельный environment file (по данным проверки — `/etc/qr_app/srv.env`). Не копировать его содержимое в репозиторий, логи, скриншоты или документацию.

## 9. Проверка и эксплуатация

Минимальные проверки перед размещением:

```text
srv:                    venv/bin/python manage.py test database
statisticsDataServer:   venv/bin/python manage.py test statisticsDatabase
control_server:         node --test
SvelteKit:              npm run check; npm run build
```

После deploy безопасные скрипты проверяют активность systemd-юнитов и HTTP-ответы. Ручная диагностика production должна начинаться с:

1. `systemctl status` нужной службы и журналы `journalctl -u …`;
2. `nginx -t` перед любой правкой Nginx;
3. локальный health check соответствующего порта;
4. только затем внешний HTTPS маршрут.

Перед любым изменением SQLite нужно сделать согласованную копию через SQLite backup, а не просто копировать активный файл. Схемы БД меняются миграциями Django.

## 10. Важные ограничения и технический долг

- В исходниках встречаются development defaults для чувствительных настроек Django/платёжного клиента. Их необходимо удалить из кода и оставить только в environment files; сами значения уже исключены из этого документа.
- `admin-interface` и ряд старых build/скриптов — наследие предыдущих развёртываний. Не возвращать их в Nginx без отдельного решения.
- Состояние активных VR-устройств в основном хранится в памяти `control_server`; перезапуск процесса сбрасывает живой список и очереди. `presenceHistory` и `uptime.json` не являются полноценной очередью сообщений.
- Статистический API имеет публично разрешённые views; следует отдельно подтвердить фактическую проверку заголовка общего секрета, ограничение Nginx/firewall и права доступа.
- Для платного доступа добавлены `viewer_session_id`, эксклюзивный headset lease и нормализация числового номера гарнитуры: `VDNH/02` и `VDNH/2` считаются одним устройством. При любых новых путях важно пользоваться общими normalizer/helpers, а не сравнивать строки напрямую.
- Данные о платёжной проблеме 25 августа 2026 года показывают, что успешное создание инвойса ещё не означает работоспособность банка. Диагностика должна включать тест карты/СБП, callback, выдачу токена, захват lease и запуск фильма.

## 11. Источники внутри проекта
