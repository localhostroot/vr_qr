## Режимы очков

Фактическое значение `FREE_VIEWER_IDS` в `/etc/qr_app/srv.env`:

- `VDNH/8`–`VDNH/50` — бесплатные;
- `VDNH/1`–`VDNH/7` — платные;
- номера вне `8`–`50` бесплатными автоматически не считаются.

ID нормализуются: `VDNH/08` и `VDNH/8` обозначают одни очки.

Бесплатный режим — постоянное свойство устройства, пока его ID находится в `FREE_VIEWER_IDS`. Прямой выбор существующего фильма в бесплатных очках разрешается без телефона, заказа и токена. `FREE_ACCESS_DURATION_HOURS=168` относится к бесплатным токенам, создаваемым через web-путь, но прямой просмотр бесплатных очков от этих токенов не зависит.

## Действующая модель запуска

### Платные очки

1. Зритель покупает один или несколько фильмов с телефона.
2. Для **каждого** фильма зритель нажимает «Смотреть» на телефоне.
3. `control_server` проверяет конкретный token + viewer ID + film ID через `resume_viewer_session`.
4. Только после успешной проверки гарнитуре отправляется `videoChangeRequested`.
5. Прямой выбор оплаченного фильма в гарнитуре не запускает его: показывается «Нажмите «Смотреть» на телефоне, чтобы запустить фильм.»
6. Прямой выбор неоплаченного фильма останавливается и показывает:

   ```text
   Оплатите фильм по QR-коду,
   нанесенному на очки,
   затем нажмите «Смотреть» на телефоне.
   ```

Каждый старт проверяется отдельно. Эксклюзивный lease между разными телефонами текущим `resume_viewer_session` не применяется; поле `headset_session_active` и endpoint `end_viewer_session` остались в Django как наследие прежней модели.

### Бесплатные очки

Прямой выбор любого существующего фильма разрешён самим `FREE_VIEWER_IDS`. Телефон, корзина и бесплатный токен для этого не требуются. Утренняя очистка не может отменить этот direct-access, пока ID остаётся в server environment.

### Потеря связи

- Если гарнитура связана с `control_server`, но Django API проверки оплаты недоступен, фильм останавливается и показывается сообщение о невозможности проверить оплату.
- Если сама гарнитура потеряла связь с `control_server`, сервер не может остановить локальный плеер. Плеер переходит в offline-поведение и может показывать/запускать локальный каталог. Это осознанный fail-open компромисс, ранее подтверждённый пользователем.

## Таймеры

- Нативный `preset.resetTimeout` в текущем шаблоне гарнитуры: 60 секунд отсутствия до главного экрана блокировки.
- Серверный fallback показа сообщения после команды stop: 3 секунды.
- Сохранение in-memory playback при WebSocket reconnect: 30 секунд; после этого незавершённая статистика закрывается как `disconnect_timeout`.
- Server-side таймера отсутствия зрителя на 10 минут и grace разблокировки на 30 секунд в текущем `control_server` **нет**.
- Утренняя maintenance-задача: ежедневно в 06:00 MSK, persistent.

## Утренняя maintenance-задача

`qr-access-maintenance.service` выполняет последовательно:

1. `backup_database --destination /opt/qr_app/backups/daily-db --keep 14`;
2. `cleanup_access_state`.

Cleanup деактивирует истёкшие платные токены, а среди бесплатных — истёкшие либо относящиеся к устройствам, удалённым из `FREE_VIEWER_IDS`. Заказы и состав прав сохраняются для аудита. Активные неистёкшие бесплатные токены текущего диапазона сохраняются.

## Мониторинг и администрирование

- `/` — мониторинг очков; защищён общей Django-сессией site-admin.
- `/site-admin` — поиск заказов, ручное подтверждение оплаты и выдача токена; защищён той же сессией.
- `/stats` — отдельная статистика с собственной frontend-аутентификацией.
- Пароль site-admin присутствует в `/etc/qr_app/srv.env`; значение в Git не хранится.
- `getVrOverview` возвращает online/offline и `connectionHealth`.
- Connection monitoring считает WebSocket-разрывы control_server, а не физическое состояние Wi-Fi. Заснувший/закрывший WebSocket плеер считается offline даже при сохранённом Wi-Fi соединении ОС.

## Подтверждённые риски

1. `addToQueue` и `fillQueue` остаются на WebSocket API без платёжной авторизации и могут обойти штатную проверку. Штатная кнопка «Смотреть» использует `videoForClient`; кнопка старого queue-path скрыта, но endpoint остаётся.
2. Повторный запрос того же фильма, если он уже current/queue/pending, возвращает успешный duplicate и не перематывает фильм к началу.
3. Перезапуск `control_server` теряет живые очереди и активное in-memory состояние; права оплаты в Django-БД сохраняются.
4. В исходниках остаются чувствительные development defaults и примеры с реквизитами. Их надо вынести в environment отдельным безопасным изменением.
5. Runtime production не Git checkout, поэтому «push выполнен» и «deploy выполнен» — разные факты.
